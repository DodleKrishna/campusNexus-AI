# CLAUDE.md

Permanent engineering instructions for CampusNexus AI. Read this before doing any work in this repo.

## Project Goal

CampusNexus is a **goal-driven multi-agent campus operating system** — not a chatbot. A student states a goal
("help me plan my semester," "find internships matching my major," "resolve this hostel complaint"), and a
network of cooperating agents plans, gathers evidence, calculates against official rules, and executes real
actions on the student's behalf, with humans approving anything sensitive. Every action is auditable.

## Frozen Architecture

The following 10 runtime components are **frozen**. Do not rename, merge, split, or add peer components without
an explicit user decision. Component 10 (Context Service) is a **service**, not an autonomous agent — it never
plans or reasons, it only reads/writes shared state.

1. **Mission Orchestrator** — decomposes a student goal into a plan, sequences/dispatches sub-agents, tracks
   mission state, handles replanning on failure.
2. **Academic Agent** — coursework, grades, degree progress, academic policy questions.
3. **Career Agent** — internships, jobs, resume/skill guidance, employer interactions.
4. **Events & Opportunity Agent** — campus events, clubs, scholarships, competitions, deadlines.
5. **Campus Services Agent** — hostel, fees, facilities, IT helpdesk, administrative requests.
6. **Knowledge/RAG Agent** — retrieves evidence from the knowledge base for any factual claim other agents rely on.
7. **Action Agent** — the only component permitted to invoke external side-effecting tools (submit form, send
   email, book resource, file ticket, etc.). No other agent calls tools directly.
8. **Deterministic Verifier** — non-LLM code that checks plans/actions against official rules
   (eligibility formulas, deadlines, quotas, prerequisites) before and after execution.
9. **Approval Gate** — enforces human-in-the-loop approval for sensitive/irreversible actions before the Action
   Agent is allowed to execute them.
10. **Context Service** (service, not an agent) — the single source of truth for mission/session state, agent
    outputs, approvals, and audit trail. No planning or reasoning logic lives here.

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for data flow, module layout, and interaction diagrams.

## Core Principle (non-negotiable)

> LLMs plan/reason. Agents collaborate. RAG provides evidence. Deterministic code calculates official rules.
> Controlled tools execute. The Verifier validates. Humans approve sensitive actions. Audit logs record everything.

Concretely:

- **Deterministic vs LLM boundary**: any calculation with an official/correct answer (eligibility, GPA, fee
  amounts, deadlines, quotas, prerequisite checks) MUST be plain Python, not an LLM call. LLMs may read the
  deterministic result and explain it, but never compute it and never override it.
- LLMs choose *what to do*; they never directly produce *what happens in the world*. That path always goes
  through: Verifier (pre-check) → Approval Gate (if sensitive) → Action Agent (execute) → Verifier (post-check).

## Structured Output Requirement

Every LLM call between agents, and every agent-to-orchestrator handoff, MUST use a Pydantic model as the
output schema (function-calling / structured output, not free-text parsing). No agent may pass free-form prose
across a component boundary. Free text is allowed only in the final user-facing response.

## Tool Security Rules

- Only the **Action Agent** may invoke side-effecting tools. Other agents may only call read-only/retrieval
  tools (search, lookup, RAG query).
- Every tool has an explicit allowlist of parameters; no tool accepts arbitrary/raw code or SQL from an LLM.
- Any tool call that is irreversible, external-facing, financial, or affects another person MUST pass through
  the Approval Gate first — no exceptions, no "trusted agent" bypass.
- Tool inputs generated by an LLM are validated (Pydantic + Verifier) before execution, never executed raw.

## RAG / Evidence Rules

- Any factual claim about campus policy, deadlines, eligibility text, or procedures MUST be grounded in a
  retrieved document from the Knowledge/RAG Agent (ChromaDB), with the source attached.
- Agents must not assert policy facts from LLM parametric memory. If retrieval finds nothing relevant, the
  agent must say so rather than guessing.
- Retrieved evidence is passed as structured citations (doc id, snippet, source) alongside any answer that
  depends on it, so the Verifier and the user can trace the claim.

## Permission / Approval Rules

- The Approval Gate is mandatory for: anything irreversible, anything touching money, anything sent to a third
  party (email, form submission, booking), and anything acting on behalf of the student toward another person
  or office.
- Read-only / informational actions (answering questions, showing plans, summarizing) do not require approval.
- An approval decision (approve/reject/edit) is recorded in the Context Service audit trail with who, what,
  and when — pending human approvals must never silently expire into an auto-approve.

## Post-Condition Verification

- Every action executed by the Action Agent is followed by a Deterministic Verifier post-check confirming the
  world state actually changed as intended (not just "tool call returned 200").
- If post-condition verification fails, the mission is marked failed/needs-replan — it is never silently
  swallowed or retried blindly.

## Idempotency Requirement

- Every tool the Action Agent can call must be safe to retry: use idempotency keys / natural dedup checks so
  a retried mission step never double-submits, double-books, or double-charges.
- Mission steps are tracked by id in the Context Service so the Orchestrator can detect "already executed"
  before dispatching a repeat action.

## Testing Rules

- `pytest` is the only test runner. New logic in the Verifier or any deterministic rule module requires unit
  tests before it's considered done.
- Deterministic rule functions must have tests covering boundary conditions (exact deadline, exact quota),
  not just the happy path.
- Agent orchestration logic is tested with mocked LLM/tool calls — tests must not depend on live LLM output.
- Tool execution paths need a test proving the Approval Gate is actually enforced (no bypass regression).

## Coding Conventions

- Python, type-hinted throughout; Pydantic models for all cross-boundary data.
- FastAPI for service endpoints; LangGraph for agent/graph orchestration; SQLAlchemy models for anything
  persisted in SQLite.
- One agent = one module/package; no agent imports another agent's internals directly — they communicate only
  through the Orchestrator/Context Service using their Pydantic schemas.
- No inline secrets/config; use environment variables.
- Keep functions small and single-purpose; deterministic rule logic stays separate from any LLM-prompting code.

## Important Development Commands

FastAPI/`uvicorn` and the Streamlit UI are not yet scaffolded (Phase 2 is database + Context Service; Phase 3 adds
Knowledge/RAG retrieval infrastructure only -- no agents, no orchestration yet). What exists and works today:

```
# Install dependencies (editable install, plus pytest)
pip install -e ".[dev]"

# Initialize the dev database and load idempotent seed data
python scripts/seed_data.py

# Ingest the policy document corpus (data/policies/) into the Chroma vector store.
# Idempotent -- safe to re-run any time the corpus changes.
python scripts/ingest_policies.py

# Run the test suite
pytest

# Run the deterministic RAG retrieval evaluation (no LLM judge; exits non-zero on failure)
python eval/run_rag_eval.py
```

The dev database path defaults to `data/campusnexus.db` and is configurable via `CAMPUSNEXUS_DB_PATH` (see
`.env.example`). The test suite never touches the dev database -- each test gets its own temp SQLite file. The
same isolation applies to RAG: the dev vector store defaults to `data/chroma` (`CAMPUSNEXUS_VECTOR_STORE_PATH`),
and the test suite always ingests into its own temp Chroma collection with the offline deterministic embedding
provider, never the dev store or a network-backed embedding model. See docs/ARCHITECTURE.md for the RAG design.

## Definition of Done

A change is done only when:

1. It respects the frozen architecture and the deterministic-vs-LLM boundary above.
2. All cross-boundary data uses Pydantic structured output.
3. Any side-effecting action goes through Verifier → Approval Gate (if sensitive) → Action Agent → Verifier.
4. Relevant `pytest` tests are added/updated and pass.
5. No policy/fact claim is made without RAG-backed evidence.
6. The audit trail captures the action and any approval decision.
